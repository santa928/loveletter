# Midnight Masquerade: 密書の夜会 - 初版設計書

## 1. 目的

会社や親戚の集まりで、スマートフォン1台を順に手渡して遊べる、華やかな短時間カードゲームを公開する。初版はアークライト版『Love Letter』基本16枚のゲーム処理を基準にしつつ、タイトル、物語、役職名、説明文、画像、音、画面演出は `Midnight Masquerade: 密書の夜会` の独自表現として制作する。

初期公開先は GitHub Pages とし、遊べるオフライン版を完成させてから、独自ルールの検討および Vercel + Supabase による合言葉オンライン対戦を次段階で扱う。

## 2. 公開と表現の境界

- 初版のルール基準は、アークライト公式ルールブックの基本カード16枚、2〜4人、所要時間約5分の構成とする。
- 原作タイトルをサービス名やロゴへ使用しない。
- 原作の固有名詞、物語、カード説明文、画像、アイコン、レイアウトは複製せず、すべて独自表現へ置き換える。
- 公開版は原作商品の代替物や公式版を称さず、独自のデジタルゲームとして表示する。
- 本方針は公開リスクを抑えるための制作境界であり、法的保証を意味しない。

参照一次情報:

- アークライト公式ルールブック: <https://www.arclight.co.jp/ag/ll/rule/LoveLetter_WebRule.pdf>
- U.S. Copyright Office Circular 33: <https://www.copyright.gov/circs/circ33.pdf>

## 4. 公式ルール突合による確定処理

検討中に別版由来の処理が混在したため、REQ-001 を優先して以下を確定仕様とする。

| 論点 | 確定仕様 |
| --- | --- |
| 位階7 `総支配人` | 手札2枚の位階合計が12以上になった時点で、そのプレイヤーは即座に退出する。使用を強制する処理ではない。 |
| 位階4 `仮面の侍女` | 次の自分の手番まで他者効果を無効化する。保護中の相手は対象に指定できるが、効果は発生しない。 |
| 位階5 `演出家` | 山札が空の状態で引き直しが必要になった場合、開始時に伏せて除外したカードを引く。 |
| 3点先取戦 | ラウンド勝者は1点。引き分け時は該当者全員が得点する。得点者の最終手札が位階8であればその者は2点を得る。直前ラウンドで得点したプレイヤーを次ラウンドの開始者とする。 |

## 5. ゲームの物語と役職

プレイヤーは仮面舞踏会に招かれた客であり、夜会を仕切る主催者へ秘密の密書を届けようとする。各自は密書を預けた協力者を1人だけ保持し、他の招待客の介入をかわしながら、最後まで最も影響力のある協力者へ密書を託す。

| 位階 | 枚数 | 役職 | 独自文面で表現する効果概要 |
| ---: | ---: | --- | --- |
| 1 | 5 | 門番 | 他の招待客1人と、門番以外の役職を宣言。一致すれば対象は退出する。 |
| 2 | 2 | 情報屋 | 他の招待客1人の預け先を、使用者だけが確認する。 |
| 3 | 2 | 決闘士 | 他の招待客1人と位階を非公開で比較し、低い側が退出する。同値なら変化なし。 |
| 4 | 2 | 仮面の侍女 | 次の自分の手番まで、他者から受ける効果を無効にする。 |
| 5 | 2 | 演出家 | 自分または他の招待客1人の預け先を捨てさせ、引き直させる。 |
| 6 | 1 | 交換商 | 他の招待客1人と預け先を交換する。 |
| 7 | 1 | 総支配人 | 他の高位者と同時に関与すると密書が封印され、持ち主は退出する。 |
| 8 | 1 | 夜会の主 | このカードを手放したプレイヤーは直ちに退出する。 |

## 6. ラウンド進行

### 6.1 準備

1. 16枚をシャッフルし、1枚を伏せたまま除外する。
2. 2人戦では、追加で3枚を公開除外し、公開の推理材料として表示する。
3. 各プレイヤーへ1枚ずつ手札を配る。
4. 初回の開始プレイヤーはアプリが抽選して公開する。

### 6.2 手番

1. `handoff`: 画面をロックし、次のプレイヤー名だけを表示する。
2. `turn-open`: 本人が「密書を開封する」を押し、自分の現在の手札を確認する。
3. `draw`: 山札から1枚を引く。位階7の即退出条件はこの時点で判定する。
4. `choose-card`: 退出していなければ、2枚のうち使用する1枚を選ぶ。
5. `choose-effect`: 必要な対象または宣言を段階的に選び、確定前に確認する。
6. `resolve`: 効果を解決し、公開可能な結果だけを夜会ログへ追加する。
7. `next-turn`: ラウンドが継続する場合、次の生存プレイヤーへの手渡しロックへ戻る。

### 6.3 ラウンド終了

- 1人を除いて退出した時点で、その生存者が勝者となる。
- 最後の山札を引いた手番の解決後に山札が空なら、生存者の手札を公開し、最大位階のプレイヤーが勝者となる。
- 最大位階が同じプレイヤーが複数いる場合は引き分けとする。
- 1ラウンド設定では結果画面から再戦またはタイトルへ戻れる。
- 3点先取設定では得点更新後、いずれかが3点以上へ達したら宴の最終結果を表示する。

## 7. 情報公開と秘密保持

### 7.1 公開情報

- プレイヤー名、退出状態、現在手番、山札残数、ラウンド番号、連戦時の得点
- 各プレイヤーの使用済みカードを順序付きで並べた捨て札
- 2人戦で公開除外された3枚
- カード使用、対象指定、効果が無効になった事実、退出、勝敗の公開結果

### 7.2 非公開情報

- 各プレイヤーの現在の手札
- 開始時に伏せて除外した1枚
- 情報屋で確認したカード内容
- 交換商の交換後の保持カード内容
- 演出家による引き直し後のカード内容

### 7.3 1台端末の表示規則

- `handoff` では手札、ログ詳細、捨て札の拡大表示を隠し、端末を受け取るべき人物だけを示す。
- 秘密情報が表示される操作は、本人が開封を明示的に実行した画面内に限定する。
- 情報屋の確認結果には `確認して閉じる` を必須とし、閉じた後に公開ログから再表示できない。
- 秘密表示中に次手番案内や端末を渡すCTAを併置しない。

### 8.3 配置原則

- 主対象はスマートフォン縦画面 `390x844` および `430x932` とする。
- 公開盤面のアンカーはカード操作領域とし、手札を画面下部、公開HUDを上部、確認CTAを安全余白付きの最下部に配置する。
- 捨て札履歴は折りたたみ可能にし、手札選択領域と重ならない。
- カード、モーダル、CTA は子要素の実寸から余白を決め、下端および右端のはみ出しをランタイム計測でも検証可能にする。

## 9. 技術構成

### 9.1 初版スタック

- `Vite + React + TypeScript`
- UIはDOM中心とし、操作性、読み上げ対応、秘密表示の明確な画面遷移を優先する。
- アニメーションはCSSを基本とし、必要な短い祝福演出のみ軽量な追加表現を検討する。
- 開発サーバ、依存導入、テスト、ビルドは Docker コンテナ内で実行する。

### 9.2 境界

ゲームロジックはUIから分離し、後続のオンライン版が同じルール判定を利用できるようにする。

```ts
type GamePhase =
  | "setup"
  | "handoff"
  | "turn"
  | "private-reveal"
  | "resolution"
  | "round-result"
  | "match-result";

type PlayerAction =
  | { type: "start_round" }
  | { type: "open_handoff"; playerId: string }
  | { type: "play_card"; cardId: string }
  | { type: "select_target"; targetId: string }
  | { type: "declare_role"; rank: number }
  | { type: "close_private_reveal" }
  | { type: "start_next_round" };
```

- ルールエンジン: 山札、手札、効果、保護、退出、ラウンド勝者、得点を決定する純粋関数群。
- UI状態: 秘密情報をいつ表示できるかと、公開ログをどう表示するかを管理する。
- 保存: 初版は進行中ゲームを端末内にのみ保持し、タイトル画面から保存データを消去できる。
- アセット: 画像と音は静的アセットとして配信し、動的な文言や数値はHTMLで表示する。

## 10. アセットと演出

### 10.1 Image genで作成する基準画像と素材

- `390x844` 縦型ゲーム画面の基準UI画像
- タイトル背景となる仮面舞踏会の大広間
- カード背面と共通の金箔カードフレーム
- 手渡しロック画面の封蝋付き密書
- ラウンド勝利および最終優勝の祝福背景
- 8役職それぞれの独自の仮面肖像イラスト

生成画像は実装前に目視確認し、採用画像をプロジェクト配下へ保存してからコードに組み込む。画像へカード名・効果説明・得点などの可変テキストを焼き込まず、表示テキストはHTMLで重ねる。

### 10.2 音と動き

- 効果音: 招待状の開封、封蝋解除、カード配置、退出、ラウンド勝利、最終優勝
- 常設操作: ミュート切替。ユーザー操作前の音声自動再生は行わない。
- 動き: 手渡し開封、カード選択、効果確定、結果表示に絞り、受け渡しテンポを損なう長い演出は採用しない。

初版では実装対象外とし、次段階の設計条件のみ固定する。

- 合言葉で参加するルーム方式とする。
- Supabase側が権威あるゲーム状態と手番判定を保持し、端末へは閲覧権限のある情報だけを返す。
- パスプレイ用の秘密表示をオンライン通信へ流用せず、プレイヤーごとの公開/非公開ビューを新たに設計する。
- 独自ルールの導入判断は、初版プレイテストの結果を得た後に行う。

## 12. エラー処理と安全策

- 使用できないカードまたは必要な対象がない状態では、UIに理由を示して無効操作を防ぐ。
- 保護中の招待客を対象に取った場合は、使用自体は成立させた上で、効果が無効だったことのみを公開ログに記録する。
- ブラウザ再読込で進行データが復元できない場合は、新規夜会へ戻す前に状態を消去する旨を明示する。
- 保存データ消去には確認ダイアログを挟み、共有端末に秘密情報を残さない選択を提供する。

## 15. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 原作版差によるルール混同 | 公開版が「原作寄せ」の要件を満たさない | アークライト公式PDFを唯一の初版ルール基準とし、テスト名に判定条件を残す |
| 1台端末で手札が覗かれる | ゲーム体験が成立しない | 手渡しロック、秘密確認の閉鎖操作、公開ログの分離を受け入れテスト対象にする |
| 豪華な画像が可読性を下げる | カード選択ミスや遊びづらさ | フレームと背景のみ画像化し、文言・数値は高コントラストHTMLで表示する |
| 静的配信のベースパス不備 | GitHub Pagesで素材が欠落する | ベースURLを考慮したビルドとPages条件でのスモーク確認を行う |
| 将来オンライン化でロジックを再実装する | 判定差分と追加コスト | 初版からルールエンジンを副作用のないイベント処理として分離する |

## 16. 性能目標

- 一般的なスマートフォン回線で初回の操作可能表示まで3秒以内を目標とする。
- タップ後の主要UI応答は100ms以内、画面遷移アニメーションは原則500ms以内とする。
- 画像は表示サイズに合わせて最適化し、初期画面に不要な役職画像や勝利素材は遅延読込対象とする。
- 秘密確認およびカード選択中に、演出による入力ブロックを不必要に発生させない。
